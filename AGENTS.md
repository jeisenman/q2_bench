Repository instructions
Mission
Build a reliable, typed Python SDK for agent workloads. Prefer simple modules, explicit contracts, vectorized batch operations, and deterministic behavior.

Toolchain
Use uv for environments, dependencies, locking, and command execution.
Support Python 3.11 and newer.
Use NumPy for numeric batch operations; avoid Python loops over vectors where an equivalent array operation is clearer.
Run uv run python scripts/check.py before declaring work complete.
Local MCP visibility
Run MCP servers with Q2_MCP_DEBUG=1 during local development. The server writes bounded lifecycle events to stderr and includes them as debug_trace in MCP tool responses. Prompts, logs, credentials, and arbitrary production payloads are not recorded.

Runtime restart requirement
After changing an MCP server's Python code, configuration, environment variables, prompts, or dependencies, rebuild and recreate that MCP server before validating behavior. An existing process retains imported modules and environment state.

After changing MLflow server configuration, registered agents, model settings, tracking configuration, or MLflow-backed workflow code, restart the MLflow server and any dependent assistant or evaluation process before validating behavior.

A UI reload or client reconnect is not sufficient unless it also recreates the server process. Rebuild and recreate the affected Docker Compose services, for example:

docker compose up -d --build --force-recreate --wait prod-support-mcp mlflow
For host-side processes, terminate and relaunch the commands. The production-support MCP launcher loads .env and defaults to the live production source:

uv run prod-support-mcp
uv run mlflow server --host 127.0.0.1 --port 5000 \
  --backend-store-uri sqlite:///var/mlflow/backend.db \
  --default-artifact-root ./var/mlflow/artifacts
After restarting, verify the process-specific configuration in the trace or startup output. For production support, confirm PROD_SUPPORT_SOURCE=production; never treat an empty-source report as production evidence.

Use the repository restart utility for a full MCP container refresh that leaves Codex running:

uv run python scripts/restart_codex_runtime.py
Add --with-mlflow when the MLflow server also needs to be restarted. Use --dry-run first when validating the restart command.

Architecture
Production code belongs in top-level packages under src/.
The agent loop is the harness (Claude or Codex), not this repository. Baseline procedures belong in src/workspaces/<workspace>/skills/<skill_id>/; tools belong behind MCP.
Harness skill directories (.claude/skills/, .codex/skills/) are generated by agentbench sync-skills. Never edit them directly.
Whenever git diff touches src/workspaces/, run uv run agentbench sync-skills and commit the regenerated harness directories with the change. scripts/check_skills.py fails the build when they drift.
Deterministic tool compositions belong in src/workspaces/<workspace>/workflows/<workflow_name>/. A workflow fixes its control flow; if a model must choose the next step, that belongs in a skill.
Data-engineering agents belong in src/workspaces/data_engineering/agents/<agent_name>/.
Every agent must be its own package directory.
Every agent and workflow package must contain an AGENTS.md that follows docs/agent-documentation-standard.md and documents its architecture, dependencies, and workflow.
When an agent implementation approaches or exceeds 400 lines, split it into focused modules such as dates, tools, classification, reporting, and data.
Workspace benchmark tasks belong in src/workspaces/data_engineering/benchmarks/.
Retired benchmarks move to benchmarks/deprecated/ with status: deprecated and a documented reason. They are source data for new cases; never edit a retired case to match a new expectation.
New benchmark cases are built from captured traces, not written by hand, and include distractors so a case rewards discrimination over recall.
Runtime containers and connector configuration belong outside src/.
Reproducible analysis belongs in the top-level investigations/ directory.
Tests mirror production modules under tests/.
Keep integrations behind typed Protocol interfaces.
Warehouse and Cortex calls resolve per environment (dev, stage, prod, sandbox). Only the sandbox is deterministic; it is served by DuckDB over CSV fixtures whose schemas mirror the warehouse. SQL that cannot mean the same thing in every backend is rejected at the boundary, not translated.
Benchmark fixtures built from production data declare an explicit anonymization strategy for every column. An undeclared column is an error.
Keep pure domain logic independent from network and provider SDKs.
Public APIs must be exported deliberately from package __init__.py files.
Prefer immutable dataclasses and dependency injection over global state.
Code rules
No tracked source or documentation file may exceed 400 lines.
Concurrency bounds such as max_parallel limit outbound I/O fan-out only. Validate that they are at least 1 and never silently reduce a requested value. Agent-loop parallelism is owned by the harness, not this repository.
Add type annotations to all production functions.
Add concise docstrings to public modules, classes, and functions.
Raise specific exceptions with actionable messages.
Use fail-fast code: validate required inputs and configuration at boundaries, stop immediately on invalid state, and avoid silent fallbacks or partial work.
Never hide lint or type failures with broad ignores.
Never commit secrets, credentials, generated environments, or caches.
Add tests for success, boundary, and failure behavior.
Git branches
Work in the current branch. Do not create new branches, and never prefix branch names with claude/.
Change workflow
Read docs/README.md, then nearby code and tests before editing.
Keep changes scoped and preserve backward compatibility unless requested.
Update tests and documentation with behavior changes.
Update the agent's AGENTS.md when its architecture, dependencies, or workflow changes.
Run the repository quality command.
Summarize changed behavior, verification, and remaining risks.

Cloud-only Databricks work
When a project or worktree is designated cloud-only, do not run Python
locally, build or run local containers, or use Chrome or Playwright. Use
supported APIs, the native Databricks CLI, and reviewed remote notebooks.
Local filesystem operations may prepare source archives and documentation, but
all Python execution and behavioral validation must occur in Databricks.
Review notebook source before submission, pin the client and window parameters,
intercept uploads for read-only integration tests, and retrieve run output
through the Jobs API. See DATABRICKS.md for the operating procedure.

Each time you add a new feature, fully restart the MCP!
